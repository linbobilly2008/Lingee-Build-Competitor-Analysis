02
核心结论摘要
总体评价
Salesforce Agentforce 是目前企业级 Agentic AI 领域最完整的产品之一。其核心竞争力不在于单一功能的领先，而在于
全生命周期闭环能力
（从构建到监控的完整链路）、
CRM 原生数据优势
（Data Cloud 作为智能体记忆）和
开放生态策略
（MCP + A2A + AgentExchange 三重开放）。对金蝶灵基 Build 而言，Agentforce 在智能体构建深度、测试体系完善度、可观测性建设三个方向上具有显著的借鉴价值。
对金蝶灵基 Build 的关键借鉴点
1. 三模式构建范式（自然语言 + 低代码画布 + Pro-code 脚本）：
Agentforce Builder 支持三种开发模式无缝切换，其中 Agent Script（声明式脚本语言）是其最具差异化的能力——将智能体行为定义为可版本控制的文本文件，实现了 AI 行为的确定性管理。灵基 Build 可借鉴其"Agent Script"理念，为高级用户提供精确控制智能体行为的专业工具。
来源：
Agentforce Builder
|
Context Engineering Guide
2. 结构化测试体系（测试套件 + 评估维度 + AI 用例生成）：
Agentforce 的测试套件包含 Response/Subagent/Actions 三类默认评估 + Completeness/Coherence/Conciseness/Latency 四类质量评估，并支持 AI 自动生成测试用例。这种多维度、可量化的测试机制远超"对话式手动测试"的常规做法，是灵基 Build 智能体测试能力的重要参考方向。
来源：产品截图 — 测试套件模块
3. 六维可观测性看板（效力/用法/满意度/质量/健康/信任度）：
Agentforce 分析模块提供了从使用量到用户满意度、从响应质量到系统健康的全面监控。特别是"粘性率"（Stickiness Rate）和"信任度"指标的设计，体现了 Salesforce 对 AI 智能体运营成熟度的深刻理解。灵基 Build 应规划类似的多维度运营分析能力。
来源：产品截图 — 分析模块 |
Agentforce 360 Observability
4. "确定性三明治"架构模式（Deterministic Sandwich）：
Salesforce 提出的"代码处理入口 → AI 处理中间不可预测部分 → 代码处理出口"的混合推理模式，是解决企业级 AI 不可控风险的关键架构范式。灵基 Build 可将此模式融入智能体编排引擎，确保关键业务环节的确定性执行。
来源：
Context Engineering Guide
5. MCP 开放标准 + AgentExchange 生态市场：
Agentforce 通过 MCP 协议实现标准化外部工具连接，配合 AgentExchange 市场的审核分发机制，形成了"协议标准 + 市场生态"的双轮驱动。灵基 Build 可借鉴此模式，建立金蝶 ISV 生态中的智能体与技能市场。

需规避的风险
1. 避免照搬"通用 Agent 平台"定位：
Agentforce 的成功建立在其 CRM 数据优势和 Salesforce 生态基础之上。灵基 Build 不应追求"通用 Agent 平台"的广覆盖，而应聚焦"ERP 原生智能体"的深度差异——33 年企业管理实践的本体知识是 Salesforce 不具备的核心壁垒。
[分析]
2. 警惕过度复杂化带来的学习曲线：
Agentforce Studio 的 10 大功能模块（智能体/测试/提示模板/数据/AI 模型/DX/分析/优化/评分器/Vibes）虽然功能全面，但界面信息密度高、功能入口分散，新用户上手成本较高。灵基 Build 应坚持"对话即开发"的简洁理念，将高级功能渐进式暴露。
3. 消费制定价模式的企业接受度风险：
Agentforce 的 Flex Credits 模式（20 Credits/标准动作、30 Credits/语音动作）虽然灵活，但"未使用额度不滚存"的政策和难以预估的消耗量可能引发企业客户的成本焦虑。灵基 Build 在制定定价策略时需充分考虑中国企业对"可控成本"的偏好。

来源：截图 — 01_新建智能体_模板库.png / 01_新建智能体_智能体模板详情.png
Agent Script：声明式智能体语言
Agent Script 是 Salesforce 为 Agentforce 设计的专属声明式语言，以纯文本文件定义智能体行为。从截图和官方文档可见，其语法包含智能体元数据（名称、ID、描述）、子智能体引用（以 # 标记，如 #GeneralFAQ）、变量声明、连接配置等模块化组件。Salesforce 将其定义为"用结构化业务逻辑替代过载的系统提示词"的统一语言。
Agent Script 的核心价值在于：（1）可版本控制——文本文件天然适配 Git 工作流；（2）可审计——行为定义透明可读；（3）可组合——指令、动作、子智能体作为模块化组件复用。这代表了从"提示词工程"到"上下文工程"的范式转变。
Agent Script Canvas 视图：交互设计与核心语言特性
Agent Script 提供了 Canvas 视图，通过快捷键驱动的交互设计大幅降低了编排门槛，同时以四大核心语言特性保证了表达能力的完备性。

变量管理系统（Variable Management）
Agentforce Builder 提供了完善的变量管理体系，支持两类变量：
自定义变量（Custom Variables）
和
消息传递会话变量（Messaging Session Variables）
。变量系统是智能体状态管理和上下文传递的核心基础设施。
自定义变量（Custom Variables）
用户自主定义的变量，每个变量包含三个核心属性：
名称（Name）
——变量的标识符；
类型（Type）
——支持文本、数字、布尔值等数据类型；
默认值（Default Value）
——变量初始化时的预设值。自定义变量可用于存储智能体运行过程中的中间状态、用户偏好、业务参数等。截图显示创建界面提供清晰的表单式配置体验。
来源：截图 — 01_Agentforce生成器_变量.png / 01_Agentforce生成器_变量_创建自定义变量.png
消息传递会话变量（Session Variables）
系统预提供的变量，以
$Session
命名空间组织，如
$Session.UserId
（当前用户 ID）、
$Session.ChannelId
（渠道标识）等。这些变量由运行时环境自动注入，智能体可直接引用获取当前会话上下文信息。截图显示添加会话变量时提供变量列表和描述信息。
来源：截图 — 01_Agentforce生成器_变量_添加消息传递会话变量.png
变量系统的一个关键设计是
跨子智能体可访问性
——自定义变量在父智能体和所有子智能体之间共享，实现了多智能体协作时的状态同步。这意味着子智能体 A 设置的变量值可以被子智能体 B 读取和使用，为复杂的多智能体协作场景提供了数据流通的基础通道。
对灵基 Build 的启示：
灵基 Build 可借鉴 Agentforce 的"双层变量体系"设计：（1）自定义变量赋予开发者灵活的状态管理能力；（2）系统会话变量提供标准化的上下文信息。特别是变量跨子智能体共享的机制，对多智能体协作场景至关重要——建议灵基 Build 在技能（Skill）之间建立类似的数据传递通道。

多智能体编排（Multi-Agent Orchestration，Beta）
Agentforce 的多智能体编排能力正在从"简单的父子关系"向"复杂的协作网络"演进。当前 Beta 版本的架构包含三个层级：
第一层：父智能体 + 子智能体层级。
父智能体作为统一入口，通过 Agent Router 将用户请求分发到对应的子智能体。子智能体独立执行任务并返回结果。
第二层：委派智能体（Delegated Agents）。
支持将任务委派给外部平台的智能体系统，实现跨平台协作。这一能力基于 A2A（Agent-to-Agent）协议，使 Agentforce 能够作为编排中心协调多个异构智能体系统。
第三层：Agent Router 智能路由。
路由器不仅基于意图分类进行静态分发，还支持基于上下文的动态路由决策，使复杂场景下的任务分配更加智能。
对灵基 Build 的启示：
灵基 Build 的多智能体编排可借鉴 Agentforce 的三层架构设计，特别是"委派智能体"概念——允许金蝶苍穹平台上的智能体与外部系统（如企业微信、钉钉）的智能体进行跨平台协作。同时，Agent Router 的智能路由机制可应用于灵基 Build 的"技能路由"层，根据用户意图自动匹配最合适的技能执行路径。

—— 创建后不可变更类型虽然看似限制了灵活性，但避免了后续的数据结构混乱。灵基 Build 可在创建时提供更充分的类型引导，而非允许事后变更。

4.6.1 架构决策：测试套件与版本绑定
测试套件采用一个重要的架构决策 ——

Trust Layer 毒性评分与审计分析
Einstein Trust Layer 在数据屏蔽之外，还提供内容安全评估、全链路审计追踪和权限保持三大纵深防御能力
01
毒性评分（Toxicity Scoring）
Trust Layer 对 AI 生成的输出内容执行毒性评分（Toxicity Scoring），从多个维度量化内容中潜在的有害成分：
评分维度：
涵盖仇恨言论、暴力威胁、色情内容、骚扰性语言、歧视性表述等多个毒性类别
评分机制：
对每段输出内容生成数值化的毒性评分，而非简单的"通过/不通过"二元判断，允许企业根据自身合规要求设定阈值
审计追踪：
所有毒性评分结果作为审计跟踪（Audit Trail）的一部分，自动记录在 Data 360 中，可随时回溯审查
触发响应：
当评分超过预设阈值时，系统可自动拦截输出、替换为安全响应、或标记为需要人工审核
02
全链路审计（Audit）
Trust Layer 构建了完整的 AI 交互审计体系，确保每一次 AI 操作都透明、可追溯、可分析：
记录范围：
用户提示（Prompt）、AI 响应（Response）、以及所有信任信号（Trust Signals，包括脱敏操作、毒性评分、数据接地来源等）均被完整记录并存储在 Data 360 中
反馈闭环：
用户和管理员的反馈（如标记不恰当响应、纠正错误输出）可直接关联到对应的审计记录，用于持续改进提示模板和 Agent 行为配置
预构建分析：
提供开箱即用的报告和仪表板（Dashboard），用于分析 AI 使用模式、响应质量趋势、毒性事件频率、数据脱敏命中率等关键指标
合规导出：
审计数据支持结构化导出，满足企业合规审计、SOC 2 认证、GDPR 数据治理等监管需求
03
动态接地的权限保持（Permission-Preserving Dynamic Grounding）
当 Agent 通过 Data Cloud 进行动态数据接地（Dynamic Grounding）检索业务数据时，Trust Layer 确保所有标准 Salesforce 安全控制完整保留：
角色控制：
保留所有标准 Salesforce 角色（Role Hierarchy）和共享规则的数据可见性控制——用户只能检索到其权限范围内的数据
字段级安全：
字段级安全（Field-Level Security）策略在数据接地过程中严格执行，敏感字段（如薪资、身份证号）对无权限用户始终不可见
对象级权限：
对象级 CRUD 权限（Create/Read/Update/Delete）在 AI 检索和操作数据时完整生效
安全不降级：
AI 助手不会成为绕过权限控制的"后门"——即使用户通过自然语言请求，也无法获取超越其权限的数据

4.9.6 多 LLM 提供商管理
Agentforce 支持启用或禁用各个 LLM 提供商，企业可以根据合规要求、成本预算和性能需求灵活选择 AI 模型提供商。每个提供商可独立开关，不影响其他提供商的配置。
LLM Open Connector 与 BYOLLM 详细架构
Salesforce 通过开放连接规范和多云支持，构建灵活的 LLM 接入体系
LLM Open Connector
开放模型连接规范
LLM Open Connector 是 Salesforce 定义的标准化 API 规范，用于将任意自定义大语言模型（包括企业自托管模型）接入 Einstein 平台：
开放规范：
定义了统一的请求/响应格式、认证协议、流式输出接口和错误处理标准，任何符合规范的模型端点均可接入
自托管支持：
企业可将部署在自有基础设施（如 vLLM、TGI、Ollama 等推理框架）上的模型通过 Open Connector 接入 Salesforce 平台
开源实现：
参考实现在 GitHub 上开源，开发者可直接基于开源代码构建自定义 Connector
Trust Layer 兼容：
通过 Open Connector 接入的模型同样受 Einstein Trust Layer 保护，数据脱敏、毒性检测等安全机制自动生效
BYOLLM（Bring Your Own LLM）
多云模型提供商支持
BYOLLM 允许企业将已有的大模型 API 密钥和部署实例直接接入 Salesforce，支持四大主流提供商：
OpenAI：
支持 GPT-4o、GPT-4 Turbo 等模型，使用 API Key 直接接入
Azure OpenAI：
支持企业通过 Azure 部署的 OpenAI 模型，使用 Azure 资源端点和密钥接入
Google Vertex AI：
支持 Gemini 系列模型，通过 Google Cloud 项目和服务账号接入
Amazon Bedrock：
支持 Claude、Titan、Llama 等 Bedrock 托管模型，通过 AWS IAM 认证接入
Models API
程序化模型调用接口
Models API 提供程序化调用大模型的标准接口，支持 Apex 类和 REST 端点两种方式：
Apex 调用：
通过
ai.Models
Apex 类在 Salesforce 服务端代码中直接调用模型推理能力
REST 端点：
通过标准 REST API 端点从外部系统调用模型，支持同步和流式响应
合作伙伴支持：
原生集成 Anthropic（Claude）、Google（Gemini）、OpenAI（GPT）三大合作伙伴的模型
统一接口：
无论底层模型来自哪个提供商，Models API 保持一致的调用接口，业务代码无需因模型切换而修改

版本管理机制
Agentforce 的版本管理以"草稿→提交→激活"为核心流程：（1）创建智能体后默认为"草稿"状态，支持随时保存；（2）"提交版本"将当前配置固化为正式版本，每个版本带有版本号和提交时间；（3）"激活"指定某个版本为生产版本。截图显示版本切换界面支持多版本浏览和回滚，且"版本删除"和"智能体删除"为独立操作入口，避免误操作。
对于企业级场景，Agentforce DX 进一步将版本管理与 Git 工作流集成——YAML 配置文件可纳入 Git 仓库，支持分支管理、代码审查和自动化部署管线。

用户体验
6.1
界面交互设计评估
基于对全部 196 张产品截图的逐屏分析，从五个 UX 维度对 Agentforce Studio 进行评估：
第一印象（First Impression）
Agentforce Studio 采用经典的"左侧导航 + 主内容区 + 右侧辅助面板"三栏布局，视觉风格简洁专业。顶部品牌标识清晰（"Agentforce Studio · Developer Edition"），功能分区明确（构建/观察两大板块）。新用户能在 2 秒内理解这是一个智能体开发环境。但
9 个一级导航项的信息密度较高
，初次使用可能产生选择困难。
可用性（Usability）
核心操作路径清晰：智能体列表→点击进入编辑器→配置→预览→提交版本→激活。每步操作都有明确的视觉反馈（如保存时间戳、状态标识）。
右侧 AI 对话面板的全程陪伴
是一个亮点设计——用户在任何配置步骤都可以向 AI 寻求帮助。但部分操作路径较深，如添加子智能体工具需要 4-5 步点击。
视觉层级（Visual Hierarchy）
整体视觉层级清晰：深蓝色顶栏→白色工作区→灰色辅助信息。标题层级（H1→H2→H3）通过字号和字重合理区分。标签页设计（Preview/智能体定义/画布/系统）让用户快速切换不同视图。但部分截图中的
表格列宽分配不够合理
，描述文本被截断影响信息完整性。
一致性（Consistency）
Agentforce Studio 整体保持了较高的设计一致性：统一的卡片样式、一致的按钮风格、规范的间距系统。但存在
局部不一致
：（1）Agentforce Studio 与 Einstein Studio 的导航结构和视觉风格有差异（两个系统并存）；（2）"设置"页面的布局风格与主 Studio 界面明显不同，更像传统 Salesforce 管理后台。
可访问性与企业级部署（Accessibility & Enterprise Deployment）
可访问性优势：
（1）中英文双语支持——界面元素均有中文翻译（虽然部分描述保留英文）；（2）颜色对比度整体符合 WCAG 标准；（3）操作按钮和链接有明确的 hover 和 focus 状态。
企业级部署能力：
（1）多版本管理——支持版本提交、切换、回滚；（2）权限控制——基于 Salesforce 的权限集体系；（3）多语言支持——智能体可配置多种语言；（4）语音通道——Agentforce Voice 支持自然语音对话；（5）多渠道部署——同一智能体配置可同时服务于 Chat、Voice、Slack 等多个渠道。
可访问性不足：
（1）截图中的图表 Y 轴标签存在与数据值不匹配的情况（如使用量图表显示 21 个会话但 Y 轴最大值仅 16）；（2）部分文本对比度不足（浅灰色辅助文字在白色背景上可读性偏低）。
6.2
开发者工具易用性
新手友好度：
Agentforce 在新手体验上投入显著——对话式创建、模板库、AI 辅助配置三个入口大幅降低了入门门槛。预览面板的"让我们聊天吧！"引导式设计，让用户在完成配置后立即获得互动反馈，形成正向激励循环。
专业开发者体验：
脚本视图提供代码编辑器体验（语法高亮、行号），DX 工具链（CLI/VS Code/Git）与标准软件开发流程对齐。推理过程跟踪视图是调试智能体行为的核心工具——逐步展示"我将使用…来解决这个问题"的推理链条，帮助开发者定位逻辑错误。
用户痛点识别：
（1）
功能入口分散
——智能体配置（Studio）、MCP 管理（设置）、安全策略（设置）分布在不同界面，切换成本高；（2）
设置界面风格割裂
——Studio 界面现代简洁，但设置页面仍保留传统 Salesforce 管理后台风格；（3）
信息密度偏高
——配置面板字段较多，缺乏渐进式披露机制。
需规避的用户体验风险：
灵基 Build 的"对话即开发"理念天然具有更低的入门门槛，但需警惕在功能丰富化过程中引入过多配置项，破坏简洁体验。建议采用"渐进式披露"策略——默认展示核心配置，高级选项按需展开。
用户体验小结：
Agentforce Studio 在功能完整性上表现优异，但在用户体验的"简洁性"和"一致性"上有改进空间。其最大的 UX 亮点是右侧 AI 对话面板的全程陪伴和推理过程跟踪视图，最大的痛点是功能入口分散和设置界面风格割裂。

Agentforce 员工场景部署策略
补充分析
基于
Agentforce for Employees
官方页面的专项分析
Salesforce 将"面向员工"作为 Agentforce 的重要应用场景单独推广，其部署策略在安全治理、渠道整合和用户体验三个层面有独到设计：
安全治理：ABAC 权限模型
Agentforce 的员工场景采用
基于属性的访问控制（ABAC）
模型，智能体在运行时识别当前用户身份，自动获取该用户有权访问的数据。管理员通过自定义 ABAC 策略精细控制智能体的数据访问范围，而非简单地"全有或全无"。此外，系统支持通过
权限集（Permission Sets）
为用户分配特定的智能体访问权限，并在运行时持续进行权限检查。这种"身份感知 + 策略驱动 + 运行时校验"的三层安全机制，确保智能体不会越权访问敏感数据。
渠道整合：Slack 作为核心协作平台
Agentforce 深度集成 Slack 作为员工场景的核心协作渠道。员工可以在 Slack 中通过
@-mention
调用智能体，智能体以"队友"身份参与对话、提供上下文信息并推动对话前进。特别值得关注的是，Agentforce 能够利用
Slack 对话数据（包括非结构化文本和音频文件）
作为知识来源，这意味着过往的团队讨论、会议录音都可以成为智能体的参考信息。
多平台部署
Agentforce 支持通过
预构建模板
在 Salesforce Lightning、Mobile 和 Slack 三个平台同时部署多个智能体。Agent Builder 提供引导式设置流程，预配置子智能体和 Actions，使非技术用户也能快速创建面向员工的智能体。系统还支持
动态数据屏蔽（Dynamic Data Masking）
，确保不同角色的员工只能看到其权限范围内的信息。
ROI 计算器

ReAct 提示架构
Atlas Reasoning Engine 的核心采用
ReAct Prompting（Reason-Act-Observe 循环）
架构。这是一种将推理和行动交替执行的提示策略：
Reason（推理）
—— 分析当前状态和用户意图，规划下一步行动
Act（行动）
—— 调用工具执行具体操作（Flow、Apex、API、MCP）
Observe（观察）
—— 接收工具执行结果，更新上下文状态
这三个步骤循环执行，直到推理引擎判断任务完成或达到步骤限制。这种设计确保了每一步行动都有推理依据，每一次推理都有行动验证。
Atlas 引擎五大组件
组件
职责
技术特点
Planner（规划器）
任务分解和执行计划生成
基于 ReAct 循环的多步规划
Action Selector（操作选择器）
从可用工具中选择最合适的操作
语义匹配 + 规则约束
Tool Engine（工具引擎）
执行选定的工具操作
支持 Flow、Apex、API、MCP 四类工具
Memory（记忆）
维护对话上下文和执行历史
短期记忆（对话）+ 长期记忆（知识）
Reflectors（反思器）
评估执行结果，决定是否需要重新规划
自我纠错和异常恢复
安全控制机制
白名单（Whitelists）
—— 限制智能体可调用的工具范围
验证器（Validators）
—— 在执行前验证操作参数的合法性
步骤限制器（Step Limiters）
—— 限制单次推理循环的最大步骤数，防止无限循环
Atlas 引擎设计为
模块化且模型无关（Model-Agnostic）
，可以切换底层 LLM 而不影响推理逻辑。

新增建议 O11：构建模型管理平台
P1
O11: 构建模型管理平台（Model Management Platform）
参考对象：
Agentforce Einstein Studio 的多提供商管理、Playground 测试环境和模型生命周期管理
现状差距：
灵基 Build 目前缺乏统一的模型管理能力，无法灵活切换和管理底层 LLM 提供商。
建设目标：
支持多 LLM 提供商的统一注册和独立开关控制
提供 Playground 测试环境，允许在部署前测试模型效果
建立模型版本管理和灰度发布机制
提供模型性能对比面板（成本、延迟、质量）
预期价值：
让企业根据成本和质量需求灵活选择模型，避免单一模型锁定，降低 AI 运行成本 30-50%。
官方文档新发现（2026.06 补充）：
Salesforce 的模型管理体系远不止多提供商管理，还包括三大关键组件：（1）
LLM Open Connector
—— 一套标准化 API 规范，支持将任意自定义或自托管模型（如 vLLM、TGI、Ollama 等推理框架）接入 Einstein 平台，参考实现在 GitHub 开源；（2）
BYOLLM（Bring Your Own LLM）
—— 原生支持 OpenAI、Azure OpenAI、Google Vertex AI、Amazon Bedrock 四大提供商，企业可用已有 API 密钥直接接入；（3）
Models API
—— 通过 Apex 类和 REST 端点提供程序化模型调用，支持 Anthropic（Claude）、Google（Gemini）、OpenAI（GPT）三大合作伙伴，所有调用均受 Trust Layer 保护且记录至审计日志。建议灵基 Build 参考此架构，重点支持国产大模型（通义千问、文心一言、智谱 GLM、DeepSeek、Moonshot 等）的标准化接入。
新增建议 O12：实施 RAG 质量指标体系
P0
O12: 实施 RAG 质量指标体系（RAG Quality Metrics）
参考对象：
Agentforce 分析看板的 RAG 质量三角 —— Context Relevance、Answer Relevance、Answer Faithfulness
现状差距：
灵基 Build 当前缺乏对 RAG 系统质量的量化评估能力，无法判断检索质量和生成质量。
建设目标：
实现上下文相关性（Context Relevance）自动评分 —— 检索到的内容是否与用户问题相关
实现回答相关性（Answer Relevance）自动评分 —— 生成的回答是否切中用户问题
实现回答忠实度（Answer Faithfulness）自动评分 —— 回答是否忠实于检索内容，而非幻觉
建立质量等级体系（Very Low / Low / Medium / High）和颜色编码标准
提供按子智能体、意图、操作的多维度下钻分析
预期价值：
RAG 质量指标是降低幻觉率的关键。据 Gartner 研究
[第三方]
，2026 年预计约 60% 的企业 AI 项目可能因缺乏质量监控而未能达到预期效果。

新增建议 O14：建设企业信任与安全框架
P1
O14: 建设企业信任与安全框架（Enterprise Trust & Safety Framework）
参考对象：
Agentforce Einstein Trust Layer 的数据屏蔽、提示注入检测和透明度控制
现状差距：
灵基 Build 虽有 CAICT 认证和 ISO 标准合规基础，但缺乏 AI 专项安全能力（如提示注入防护、AI 数据屏蔽）。
建设目标：
实现字段级数据屏蔽 —— 在 AI 处理过程中自动屏蔽敏感字段（工资、银行账号、身份证号等），并提供屏蔽前后预览
实现提示注入检测 —— 识别和拦截恶意提示注入攻击，防止智能体被利用进行数据窃取或越权操作
实现 AI 透明度控制 —— 可配置的透明度等级，向用户披露 AI 的使用方式和数据来源
建立完整的 AI 安全审计日志 —— 记录所有 AI 操作的输入、输出和决策依据
在现有 CAICT + ISO 27001 + ISO 42001 基础上，构建 AI 专项安全认证体系
预期价值：
企业信任是 AI Agent 大规模部署的前提。在 ERP 场景中，财务数据、员工信息和客户数据的安全保护尤为重要。金蝶已有的合规基础是优势，但需要补充 AI 专项安全能力。

建议灵基 Build 团队按照「
P0 补齐运维基础 → P1 增强平台能力 → P2 构建生态壁垒

深度分析新增的四项建议（O11-O14）填补了原有规划中在模型管理、RAG 质量、会话审计和 AI 安全四个方向的空白。结合原有的 10 项建议及补充的 O15 建议，灵基 Build 现在拥有一份覆盖 15 个方向的完整建设路线图。其中 5 项 P0 建议应在 3 个月内启动，7 项 P1 建议在 6 个月内推进，3 项 P2 建议在 12 个月内布局。核心原则是：
先建运维能力（让现有客户满意），再增平台深度（吸引新客户），最后筑生态壁垒（形成长期竞争优势）
