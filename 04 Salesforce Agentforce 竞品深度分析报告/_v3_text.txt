核心结论摘要
Agentforce 的本质不是「一个智能体构建器」，而是
把智能体作为一种新的应用形态，嵌入到 Salesforce 既有的数据（Data 360/Data Cloud）、业务逻辑（Apex/Flow/API）、信任（Einstein Trust Layer）与交付（DX/CI-CD）平台之上

✅ 对灵基 Build 的可借鉴点（TOP 6）
双视图同源
：低代码画布与可编辑「脚本/DSL」双向同步，业务人员与开发者协作不割裂——对应灵基「对话即开发」可补「对话→可视化→代码」三态互转。
工具即平台能力
：把 ERP 的标准动作（凭证、审批、单据、报表）封装为可复用「工具/Action」，让智能体直接调用 30 余年业务规则。
RAG 工程化
：检索器内置「引文/出处」机制，是企业级可信回答的标配，灵基应将引文与权限过滤做成默认能力。
测试+评分器+Trace 闭环
：把「期望子智能体/动作/响应」的回归测试 + LLM 评分器 + 逐步推理轨迹做成研发标配，是当前国内同类最稀缺的能力。
观测—优化回路
：真实会话回放、意图聚类、遵循率/毒性指标，驱动持续迭代；灵基应把「上线后表现」回灌到构建态。
信任层前置
：PII 屏蔽、审计、网关配额/ABAC 作为平台默认，而非事后补丁，契合中国企业合规诉求。
⚠️ 需规避的风险（TOP 6）
消费式计价的信任损耗
：会话/信用计费不透明、易超支，客户决策犹豫。灵基宜提供成本可预测、可封顶的定价与实时用量看板。
平台强锁定的反噬
：Agentforce 依赖 Data Cloud/CRM，迁移成本高。灵基要在「深度集成苍穹/星瀚」与「开放可移植」间取得平衡。
能力堆叠导致的认知负荷
：Studio 模块众多（Einstein Studio/网关/信任层/DX 等），新手上手陡峭。灵基应坚持「一条主线 + 渐进披露」。
Beta/预告功能兑现风险
：多智能体编排、评分器、健康监控等多为 Beta/发布期能力，避免对标尚未 GA 的承诺。
ROI 兑现难
：行业 >40% 项目将被取消，灵基要以「窄场景、可量化、快回收」打样，避免大而全。
「agent-washing」陷阱
：避免把既有助手/RPA 包装成智能体；以真实自主解决率、自动化深度为卖点。
一句话总结：
灵基 Build 应「学其闭环、用其结构、避其计费与锁定」——把 Agentforce 验证过的「分层智能体结构 + RAG 引文 + 测试/评分/Trace/优化闭环 + 信任层前置」作为研发蓝本，同时以
ERP 业务规则深度 + 可预测成本 + 开放可移植
建立差异化。

03
产品概览
Agentforce 是 Salesforce 的「数字劳动力(Digital Labor)」平台，让企业构建、定制并部署可自主完成任务的 AI 智能体。其作者工具
Agentforce Studio
由「构建(Build)」与「观察(Observe)」两大区构成，统一承载智能体、提示、数据、模型、测试、分析与优化。
产品矩阵与信息架构
从截图左侧主导航可还原 Agentforce Studio 的 IA：
构建区
含 智能体(Agent Builder)、测试(测试套件)、提示模板、数据(数据库/检索器/搜索索引)、AI 模型、Agentforce DX；
观察区
含 分析(Analytics)、优化(Optimization)、评分器(Beta)。配套设置层包含 Einstein 信任层、Agentforce 注册表(API/MCP)、Agentforce 网关(策略)。
① Agent Builder
画布/脚本双视图、子智能体、变量、连接、数据；对话式与模板创建入口。
② 数据/知识(Data 360)
数据库、检索器(RAG+引文)、向量搜索索引；构建在 Data Cloud。
③ 提示模板 + AI 模型
Prompt Builder(合并字段) + 模型库(BYO/标准模型，如 GPT-5 Mini)。
④ 测试套件 + 评分器
期望子智能体/动作/响应回归 + 自定义/LLM 评分器(Beta)。
⑤ 分析 + 优化
效力/用法/满意度/质量/健康/信任指标 + 真实会话回放与意图聚类。
⑥ Agentforce DX + 网关/信任层
CLI/CI-CD/IDE 专业代码；MCP 注册、网关策略、PII 屏蔽与审计。

04
功能模块分析
以下按「智能体构建 → 子智能体与工具 → 知识库与数据 → 提示与模型 → MCP/工具治理 → 多智能体编排」六个核心模块逐一拆解技术实现逻辑，每个模块给出对灵基的可借鉴点与风险。
4.1 智能体构建：画布 ↔ 脚本双视图 + 三入口
Agent Builder 提供
三种创建入口
：对话式创建（"您想让智能体做什么？"自然语言描述）、从模板库创建（Employee Agent / Service Agent / Sales / Field Service 等行业模板）、从脚本创建。构建态最核心的创新是
「画布」与「脚本」双视图
：画布是结构化低代码界面；脚本视图是 YAML/DSL 形态的智能体定义（system 指令、config、language、variables、subagents、tools），二者同源同步。2026 TDX 进一步推出
Agent Script（.agent 文件）
——一种强类型的智能体定义语言，可声明「何时用 LLM 推理、何时走确定性逻辑」，并被编码型 IDE（Cursor、Claude Code）原生处理。
图 2 · 对话式创建 + 模板库入口（"您想让智能体做什么？"）。来源：智能体/01_新建智能体_对话创建
图 3 · 脚本视图：智能体定义以 system/config/language/variables 结构化呈现，支持专业代码编辑与"提交至本版"。来源：智能体/01_Agentforce生成器_脚本视图
技术实现逻辑：画布操作与脚本是同一份智能体元数据的两种投影；脚本的强类型化让其可纳入版本控制与 CI/CD（见第 5 节 Agentforce DX），实现「可视化协作 + 代码可治理」。
✅ 可借鉴
灵基「对话即开发」可补齐
「对话 → 可视化画布 → 可编辑 DSL」三态互转
，让业务与开发协作不丢上下文。
沉淀
行业/职能模板库
（财务、HR、供应链等），降低冷启动成本。
⚠️ 风险
双视图同步的工程成本高，若同步不一致会损害信任；需明确「单一事实源」。
Agent Script 多为发布期能力，避免直接对标尚未稳定的 DSL 规范。
4.2 子智能体(Topic／2026-04 官方更名 Subagent)与工具(Action)：分层结构是核心抽象
Agentforce 的智能体由
主智能体 + 多个子智能体(Topic) + 工具(Action)
构成。每个子智能体 =
一段自然语言"指令"
（职责边界、护栏、升级规则）+
一组"可用于推理的工具"
。工具支持四种来源类型：
Apex（平台代码）、API（含 MuleSoft）、流(Flow，低代码自动化)、预测模型、提示模板
。工具可"创建自定义工具/创建实用程序/从资产库添加"，并在多个子智能体间复用（截图显示同一"Answer Questions with Knowledge"工具被 GeneralFAQ 与 AccountManagement 共用）。
图 4 · 添加工具：参考操作类型可选 Apex / API / 流 / 预测模型 / 提示模板——工具直接锚定平台原语。来源：智能体/01_..._创建自定义工具
图 5 · 连接(Connections)：智能体可挂载到 增强聊天/Messaging/Slack 等渠道，配置路由、行为与"上报(升级到人工)"流。来源：智能体/01_..._连接_路由
技术实现逻辑：子智能体本质是「意图域(Topic) + 工具白名单」，Atlas 推理引擎据用户意图路由到对应子智能体，再在其工具白名单内做 ReAct 式选择与调用，从而把「自由发挥」约束在可治理范围内。这与灵基「配置角色 + 技能配置」的思路高度同构。
✅ 可借鉴
「角色/Topic + 技能/工具白名单」分层
是控制 LLM 不确定性的关键，灵基应将"技能"标准化为可复用、可版本化、可跨智能体共享的资产。
把
金蝶 ERP 的标准动作
（如制单、审批、查询余额、生成报表）封装成「工具」，让工具调用即业务规则执行——这是灵基相对通用框架的最大杠杆。
内置
"升级到人工"流
作为标准护栏。
⚠️ 风险
工具与平台原语强绑定（Apex/Flow）会抬高学习门槛；灵基应让"技能"以低代码/自然语言为主，代码为辅。
资产库治理不当会导致工具泛滥、权限失控，需配套审批与权限模型。
4.3 知识库与数据：RAG 工程化 + 引文(Citation)
数据模块构成完整 RAG 链路：
数据库(导入文件/选择数据类型) → 检索器(Retriever) → 搜索索引(向量化)
。检索器生成器是一个向导：选择检索器类型 → 定义筛选器 →
配置检索结果(返回字段、结果数≤50)与引文设置
（标准引文/自定义引文，可配置出处 URL、标签），并支持"测试检索器"查看结果。搜索索引生成器支持
分块(区块) → 选择向量化策略(嵌入模型：E5 Large V2 / 多语 E5 / 多语 CLIP / Salesforce Embedding V2) → 筛选字段 → 排名 → 检查并构建
，底层运行在 Data Cloud。
图 6 · 检索器结果配置：返回字段 + "引文设置"（标准/自定义引文，含出处 URL 与标签）——为可信回答提供来源溯源。来源：数据/05_..._配置检索器结果
图 7 · 搜索索引向量化：可选多种嵌入模型；配合分块与排名构成企业级向量检索。来源：数据/06_..._向量化
技术实现逻辑：检索器把"结构化 CRM 数据 + 非结构化文档"统一为可被智能体调用的"接地(Grounding)"来源；引文机制把每条回答关联到来源链接，是降低幻觉、满足合规审计的关键。
✅ 可借鉴
引文/出处
应作为灵基知识问答的
默认能力
而非选配——企业级可信回答的底线。
检索器内置
筛选器 + 字段级权限
，确保智能体只检索用户有权访问的数据（行级/字段级权限是 ERP 场景刚需）。
提供
"测试检索器"
所见即所得，便于知识调优。
⚠️ 风险
向量索引/嵌入模型配置项过多（分块、模型、排名）对业务用户过于专业；灵基宜提供"智能默认 + 高级可调"。
强依赖自有数据平台(Data Cloud)，灵基需评估与苍穹/星瀚数据中台的接入成本与多源异构支持。
4.4 提示模板与 AI 模型：合并字段接地 + 模型可选
Prompt Builder 是三栏式工作台：左为模板设置（模型类型、模型如
GPT-5 Mini
、限制、文件排除优先级、格式、回复语言自动识别），中为提示编辑（可"插入资源/输入/操作/全局与配置"，以
Input:Account.Name
等
合并字段
将 CRM 数据注入提示），右为"已解析的提示 → 生成的响应"实时预览。AI 模型层（模型库/Einstein Studio）支持标准模型与
自带模型(BYO)
、预测模型与分类模型的训练与度量。
图 8 · Prompt Builder：合并字段接地 + 模型选择(该演示组织选用 GPT-5 Mini) + "提示→解析→响应"实时预览。来源：提示模板/03_提示模板_提示生成器
✅ 可借鉴
合并字段
把业务数据安全地注入提示，是"接地"的轻量实现；灵基可用 ERP 单据/主数据字段做同类绑定。
模型可插拔
(标准/BYO)避免被单一大模型绑死；契合国内多模型(通义/文心/DeepSeek 等)与信创诉求。
"提示→解析→响应"三段预览，降低提示工程门槛。
⚠️ 风险
提示模板与 CRM 对象耦合深，跨域复用难；灵基应保持提示资产与数据模型的适度解耦。
4.5 重点：MCP / 工具 / 网关治理（企业级开放与安全）
Agentforce 在 2025-2026 大力押注开放协议：
双向 MCP
——既能作为客户端消费外部 MCP 服务器工具，也提供
Salesforce 托管 MCP 服务器

4.6 多智能体编排（Multi-Agent Orchestration）
Summer '26（2026-06-15 GA）将多智能体编排从 Beta 转正，底座升级为
Atlas 推理引擎 3.0
：一个
编排者(Orchestrator)
接收请求后，读取已注册子智能体的描述与可用动作，把任务路由给最合适的专才子智能体；并可经 A2A 把任务委派给非 Salesforce 智能体（如 Azure 上的采购智能体、Google Cloud 上的物流智能体）。Salesforce《第 11 次连接性基准报告》（2025 年 10–11 月、1,050 名 IT 领导）：组织平均使用 12 个智能体，
预计两年内智能体数量增长 67%
，但约 50% 智能体仍处"孤岛"未编排。
✅ 可借鉴
「编排者 + 专才子智能体」是复杂企业流程的可行架构，灵基可先做
同平台内的编排
（路由/委派/汇总），再逐步开放跨系统 A2A。
编排依赖
子智能体的"自描述"（描述+动作清单）
——灵基应强制智能体/技能具备结构化元数据以支持自动路由。
⚠️ 风险
多智能体的"接缝问题"(seam problem)——路由错误、上下文丢失、成本叠加——是真实工程难点；不宜过早承诺全自治编排。
功能模块小结：
Agentforce 功能版图的真正壁垒在于「
结构化抽象(角色/Topic+工具) + 平台原语锚定(Apex/Flow/API/数据) + 开放治理(MCP/网关/注册表)

08
技术壁垒
Agentforce 的技术护城河由四块构成：
Atlas 推理引擎、Data 360 数据底座、Einstein 信任层、平台原语(Apex/Flow/Metadata)
。它们彼此咬合，单点复制易、整体复制难。
8.1 Atlas 推理引擎（ARE）
Atlas 是 Agentforce 的"大脑"，实现推理时的"System-2"思考以提升准确率、降低幻觉。其架构含
Planner(把目标拆成步骤计划)
、
Action Selector(据计划选工具/动作)
、
Tool Execution Engine(动态调用工具)
、
Memory Module(会话历史/上下文嵌入/长期记忆)
。运行机制是"
飞轮
"：从 Data Cloud 拉取结构化+非结构化数据 → 生成计划 → 评估能否达成 → 循环至自信达标。它用
Chain-of-Thought + ReAct（Reason→Act→Observe 循环）
在"Topics/子智能体(意图)"上推理并遵守业务规则；标准请求端到端约 2–5 秒。Summer '26 升级到
Atlas 3.0
作为多智能体编排的协调层。
据官方工程博客/Atlas 页与第三方解读补全
更细的引擎视图可拆为
五组件
：Planner(规划)、Action Selector(选工具)、Tool Engine(执行 Flow/Apex/API/MCP)、Memory(短期对话+长期知识)、
Reflectors(反思器，评估结果并决定是否重规划/自纠错)
；并叠加三类
安全控制
：白名单(限定可调用工具)、验证器(执行前校验参数)、步数限制器(防无限循环)。引擎
模型无关(model-agnostic)
，可切换底层 LLM 而不改推理逻辑。
注：竞品报告B 关于"Agent Script 为 TypeScript 开源语言/github 仓库/config:model=gpt-4o 语法"等具体说法，与官方开发者指南不符，本报告未采纳（详见附D）。
8.2 数据底座 / 信任层 / 平台原语
Data 360 (Data Cloud)
统一结构化/非结构化数据与实时画像，是 RAG 与接地的数据源——"数据在哪，智能体就强在哪"。
Einstein 信任层
PII 屏蔽、零数据保留、毒性检测、审计——把"可信"做进架构，而非应用层补丁。
平台原语
Apex/Flow/Metadata/MuleSoft 让工具直接复用 20 年沉淀的业务逻辑与集成。
数据训练来源：Agentforce 以"BYO/标准基础模型 + 客户自有数据接地"为主，强调
不使用客户数据训练基础模型
(信任层零保留)；预测/分类模型可在 Einstein Studio 用客户数据自训。专利与底层归属 Salesforce 平台体系(本报告不就具体专利号做未经核验的断言)。
✅ 对灵基的启示
灵基的
真壁垒应是"30 余年业务规则 + ERP 实时数据"
——对应 Atlas 的"业务规则约束 + Data 360 接地"。把业务规则做成智能体可调用的确定性逻辑，是国内对手难以复制的资产。
"规划-选工具-执行-记忆"四件套
是可参考的推理引擎抽象；灵基可在编排层引入显式 Planner + 工具选择 + 记忆。
"不用客户数据训模型 + 零保留"
应作为灵基对国央企的明确承诺。
⚠️ 风险
自研推理引擎成本高、周期长；灵基初期可"成熟开源/大模型 Agent 框架 + 业务规则层"组合，避免重复造轮子。
壁垒来自"数据×规则×平台"耦合，单独堆模型能力无法形成护城河——灵基须把资源压在"业务规则资产化"上。
技术壁垒小结：
Agentforce 的护城河不是模型，而是"
推理引擎 × 数据底座 × 信任层 × 平台原语
"的系统耦合。灵基的对位护城河是"
ERP 业务规则 × 实时经营数据
"——这正是金蝶相对通用 AI 厂商和 Salesforce(在中国本土化与 ERP 深度上)的差异化机会。
