核心结论摘要
重点呈现对灵基 Build 的可借鉴点与需规避风险。
总体判断
【分析推断】
Agentforce 的核心优势不是“能用自然语言创建智能体”，而是围绕智能体资产形成结构化定义、版本提交、Preview/Trace、测试套件、评分器、知识检索、MCP 注册、Trust Layer、Analytics、Optimization 的完整操作系统。
可借鉴点：结构化智能体资产
将智能体拆成角色、子智能体、指令、动作、规则、变量、数据、连接、权限、测试、版本。
【规划建议】
灵基 Build 应把“对话即开发”落成可迁移、可回放、可审计、可回滚的工程资产。
可借鉴点：测试与观测前置
Agentforce 将 Testing Center、Preview/Trace、Agent Analytics、Optimization 放入生命周期。
【规划建议】
灵基 Build 应把测试门禁和运行观测作为第一期平台能力，而不是上线后的补丁。
可借鉴点：MCP 与工具生态治理
Agentforce 把 MCP 包装成带 Registry、OAuth、scope、凭据、权限集、网关策略、AgentExchange 分发的企业工具治理能力。
【规划建议】
灵基 Build 可围绕 ERP 连接器、客户私有工具、ISV 行业能力建立工具注册表。
需规避风险：自然语言创建不等于生产可用
【分析推断】
若缺少测试、Trace、版本、审计、权限、脱敏、回滚和成本控制，智能体很难进入 ERP 生产系统。
【规划建议】
灵基 Build 不应把“对话即开发”窄化为生成入口。
需规避风险：Trust Layer 不能泛化宣传
Salesforce Help 展示数据屏蔽能力，但也提示 agent 场景下 LLM data masking disabled。灵基 Build 需要逐链路验证输入、RAG、工具调用、模型请求、响应、审计日志、失败回放是否真正脱敏。
需规避风险：过度后台化
【分析推断】
Agentforce 能力完整，但 Setup、Einstein Studio、Data Cloud、Agent Authoring 等入口割裂。
【规划建议】
灵基 Build 应保留统一工作台主线，让高级设置渐进展开。

产品概览
对 Agentforce 与灵基 Build 的定位、能力资产和平台差异进行总览。
S
Salesforce Agentforce
企业智能体运营平台
主体
【分析归纳】面向构建、测试、发布、观测、优化的企业智能体运营平台
以 subagent、instruction、action、rule、variable、data、connection 组织智能体资产
通过 Data 360、Flow、Apex、MuleSoft、Slack、AgentExchange 深嵌 Salesforce 生态
以 Trust Layer、ABAC、Audit/Feedback、Digital Wallet 支撑企业治理与计费
金
金蝶灵基 Build
企业级 AI 原生构建平台
核心理念是“对话即开发”，覆盖智能体、技能、应用、原型探索到生产部署
智能体开发支持自然语言创建、角色设定、技能配置、测试与提交审核
Skill 是独立业务能力模块，支持流程型、知识型、能力型，并可通过 MCP/Agent 编排
拥有 ERP 业务对象、规则、流程、权限与行业经验沉淀的场景优势

功能模块分析
按核心功能模块逐项分析：每张卡片包含技术实现逻辑、模块总结和来源。
4.1 Agentforce Studio 信息架构
技术实现逻辑：Agentforce Studio 将 Build 与 Observe 合并为智能体工作台，构建侧包含智能体、测试、提示模板、数据、AI 模型、Agentforce DX，观察侧包含分析、优化、评分器。它复用 Salesforce Setup、Einstein Studio、Data Cloud、Agent Authoring 等既有容器，获得平台能力复用，也带来跨系统跳转。
模块总结：Agentforce Studio 广度强但一致性不足。灵基 Build 应吸收其生命周期覆盖，但坚持单一工作台主线。
来源：本地截图目录 /Users/linbo/Desktop/Claude/竞品研究/Agentforce Studio截图原图；截图底稿 agentforce_screenshot_audit/screenshot_analysis.md
4.2 Agent Builder / 智能体生成器
技术实现逻辑：三栏结构由左侧对象树、中间 Preview/定义工作区、右侧 Agentforce 助手组成；对象树包含设置、系统、语言、子智能体、变量、连接、数据；支持画布视图与脚本视图，顶部提供保存、提交版本、激活/停用等操作。
模块总结：最值得借鉴的是“对话助手 + 结构化对象树 + 工程视图”组合。灵基 Build 需要业务视图和开发者视图共享同一份定义。

4.3 Subagent 与多智能体编排
技术实现逻辑：Primary Agent 作为单一入口识别意图，再由 Atlas Reasoning Engine 根据 agent description、instructions、available actions 路由到 Secondary Agents / Subagents。官方说明 multi-agent orchestration 支持统一用户体验、A2A、治理与可观测。
模块总结：灵基 Build 可围绕财务、人力、供应链建立“业务主智能体 + 专家子智能体”，同时必须做职责重叠检测、路由测试和数量治理。

4.4 Actions / Tools / ERP 连接
技术实现逻辑：公开资料确认 Agentforce 可连接 Flow、Apex、MuleSoft API、Prompt Template 等能力；截图与相关页面显示 Predictive Model、MCP Tools 是 Agentforce Studio/生态中的可用资产。Help 文档将 actions 描述为 agent 可调用工具，并强调 instructions 要具体、可测试、避免冲突。
模块总结：
【分析推断】
对 ERP 场景，Tools 不只是接口调用，而是带权限、参数、业务副作用、审批和回滚的操作资产。
【规划建议】
灵基 Build 的 Skill 应升级为可测试、可审计、可治理的工具资产。

4.5 MCP 与 AgentExchange
技术实现逻辑：MCP 注册表分 API 与 MCP Server；注册 MCP 连接需要 URL、OAuth 2.0、IdP URL、scope、client id/secret，并会创建命名凭据、外部凭据和权限集。AgentExchange 支持第三方 agents、subagents、MCP servers 的发现、采购、激活。
模块总结：
【分析推断】
MCP 的产品价值不是协议本身，而是企业工具治理和生态分发。
【规划建议】
灵基 Build 应建立企业工具注册表与 ISV 生态市场。

4.6 数据、知识库、Retriever 与 Search Index
技术实现逻辑：Agentforce 将知识 grounding 拆为 Data Library、Retriever、Search Index、RAG 多层；Search Index 支持源对象、chunk、向量化、筛选字段、排名、构建历史；Prompt Builder 可通过 individual retriever、ensemble retriever、web retriever grounding。
模块总结：
【分析推断】
企业 RAG 不是上传文件，而是数据建模、索引、检索策略、权限过滤、测试和质量评估。
【规划建议】
灵基 Build 应建设 ERP 业务语义层。

4.7 Prompt Builder、AI 模型与 Einstein Studio
技术实现逻辑：Prompt Builder 支持插入输入、操作、全局配置、资源、预览设置和 Performance Insights；Einstein Studio 覆盖分类模型、生成式模型、预测模型、模型库和 Playground。
模块总结：Agentforce 把 Prompt 和模型都资产化。灵基 Build 不应只做大模型配置，还要让预测、分类、风控、异常检测等模型成为智能体可调用能力。

4.8 测试套件、评分器与 Agentforce DX
技术实现逻辑：Testing Center 可从 core subagents/actions、knowledge content、Data Library 或上传文件生成测试用例；测试字段覆盖 Conversation History、Utterance、Expected Subagent、Expected Actions、Expected Response；支持 completeness、coherence、conciseness、latency、instruction adherence 等评估。
模块总结：
【分析推断】
Agentforce 把测试从聊天预览升级为发布门禁。
【规划建议】
灵基 Build 应将测试中心作为 P0 能力，覆盖路由、技能参数、权限、副作用、回复质量、延迟与成本。

4.9 Preview、Trace 与调试体验
技术实现逻辑：Preview 支持模拟模式与现场测试，Trace 展示输入、子智能体转换、推理说明、变量更新、耗时、父级跨度，右侧助手可解释 trace。
模块总结：
【分析推断】
Trace 是智能体从黑盒变成可审查系统的关键。
【规划建议】
灵基 Build 应为业务人员提供“为什么这样做、用了哪些数据、哪里失败、建议怎么改”的解释层。

4.10 分析、优化、健康监控
技术实现逻辑：Agent Analytics 基于 Agent Session Tracing，引用每次 LLM call，并可与 feedback、guardrails、Flex Credit analytics 关联；截图显示 Agent Performance Overview 覆盖使用情况、信任度、健康、有效性、满意度、质量，并按 actions/intents/subagents breakdown。
模块总结：
【分析推断】
Agentforce 将智能体作为生产系统运营。
【规划建议】
灵基 Build 应围绕 ERP 业务结果建设 AgentOps，例如关账效率、审批周期、库存异常处理、应收回款。

4.11 Trust Layer 与可信 AI 治理
技术实现逻辑：Einstein Trust Layer 包含安全检索、Prompt Defense、数据屏蔽、审计、反馈、毒性评分等；Data Masking 分 pattern-based 和 field-based。Help 同时提示 agent 场景下 LLM data masking disabled，需要谨慎理解覆盖范围。
模块总结：
【分析推断】
可信 AI 不是一个开关，而是构建、测试、发布、运行、审计全链路能力。
【规划建议】
灵基 Build 要把字段权限、脱敏、审批、审计责任人嵌入智能体运行链路。

用户体验分析
覆盖界面交互、操作体验、开发者工具、企业级部署和用户痛点。
界面交互设计
优点：三栏 Builder 适合复杂对象编辑，右侧助手嵌入工作流，Preview/Trace 增强透明度。问题：多个后台容器切换，中英文混杂，概念密度高。
来源：本地截图全量分析 agentforce_screenshot_audit/screenshot_analysis.md
操作体验
优点：版本、预览、提交、启停位置清楚；Search Index 有“轻松设置/高级设置”渐进设计。问题：MCP、Retriever、Trust Layer 等页面字段技术化，业务人员理解成本高。
来源：本地截图 数据、设置Einstein、智能体模块
开发者工具易用性
Agentforce DX 提供 CLI、脚本、测试 API、元数据能力，说明 Salesforce 同时面向管理员、业务配置者和开发者。灵基 Build 也需要 CLI/导出/版本化/CI/CD/测试 API。
来源：Developer Guide
https://developer.salesforce.com/docs/ai/agentforce/guide/get-started.html
；本地截图 Agentforce DX
企业级部署能力
Agentforce 支持多渠道部署，connection 可包含 behind-the-scenes instructions、adaptive response formats 和 Omni-Channel flows。灵基 Build 应把发布前测试、权限、成本、回滚与渠道适配统一成发布检查清单。
来源：Deploy Your Agent to Channels
https://help.salesforce.com/s/articleView?id=ai.agent_parent_deploy.htm&type=5&language=en_US
核心用户痛点
Agentforce 暴露的痛点是企业智能体平台很容易过重：数据、模型、工具、权限、渠道、观测都必要，但若缺少统一任务流，业务用户会迷失。灵基 Build 应用业务语言包装高级能力。

https://www.kingdee.com/docs/lingee#lingji-build-guide
